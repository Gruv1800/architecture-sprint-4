# Планирование: анализ, идентификация проблем и поиск решений

**Существующие проблемные места**

- Отсутствует возможность горизонтального масштабирования MES контейнера
- Базы данных развернуты в single node режиме. Отсутствует репликация.
- Отсутствие кэша "новых заказов" для отображения в MES UI
- Ручной деплоймент в prod и pre-prod окружения

**Потенциальные проблемные места**

- С ростом количества клиентов Shop API и MES API могут стать узкими местами. Возможны задержки в обслуживании запросов.
- Медленная запись и\или чтение из БД
- Медленная обработка запросов на создание заказа из-за необходимости загрузки моделей в S3 Storage

**Инициативы по устранению нежелательных ситуаций**

- Предусмотреть возможность горизонтального масштабирования Shop API, MES и MES API
- Репликация БД master-slave
- Разделение потоков данных: запись\изменение на master, а чтение на read only реплику БД
- Реализация асинхронной загрузки файлов в S3 Storage. Позволит быстрее отвечать на запросы в Shop API
- Добавление кэша "новых заказов" для ускорения загрузки UI оператора.

**Ключевые аспекты целевой архитектуры**

- Повышенная отказоустойчивость и пропускная способность за счет репликации и горизонтального масштабирования
- Уменьшение времени ответа по основному API за счет кэширования и асинхронной загрузки моделей

## Дополнения по результатам ревью

1. В текущей архитектуре все клиенты жестко завязаны на определенные версии API (MES, CRM и Shop), что привносит дополнительные сложности при добавлении новых фич, а так же может поломать обратную совместимость. В целевой архитектуре предлагается разорвать жесткую связность между клиентами и конечным API с помощью поддержания версионирования и выгрузки спецификаций в Spec Storage (API Curio Registry).
2. Нарушен ряд подходов к организации микросервисной архитектуры:

    - Единая БД для CRM и Shop API. Чревато выходом из строя двух компонентов, если что-либо случится с общей БД;
    - Отсутствует API Gateway. Влечет за собой сложности маршрутизации запросов при дальнейшем масштабировании системы, а так же невозможность применить централизованные инструменты обеспечения безопасности (фильтры, правила, рейт-лимитер и т.п).
    - Не предусмотренно горизонтальное масштабирование компонентов;
    - Отсутствует разделение потоков на чтение\запись для оптимизации работы с БД (CQRS паттерн).
3. Для того, чтоб определить, какую нагрузку способна выдержать система необходимо учесть несколько показателей:

    - Количество доступных ресурсов. В нашем случае это потоки веб-серверов (для API), а так же память и CPU для MES (т.к. производятся сложные расчеты);
    - Учесть возможность параллелизма (х кол-во ядер CPU);
    - Произвести замеры времени среднего ответа системы на запрос (создание заказа);
   На начальных этапах можно придерживаться формулы  -  **RPS = Потоки(веб-сервера) / Среднее время ответа**. С учетом параллелизма данный результат можно умножить на количество потоков в тред-пуле (или ориентироваться на количество ядер) в рамках которого будут производиться основная обработка запросов.
4. Тормоза в системе:
    - Долгая обработка заказов. Пользователям приходится ждать сверх установленного времени для получения своих заказов.
    - Долгая загрузка списка заказов в UI операторов.
5. В текущей реализации у системы полностью отсутствует наблюдаемость: трассировка, логирование, сбор метрик, алерты. Данный факт не позволяет проводить мероприятия по предотвращению возникновения сбоев в системе, а так же усложняет диагностику возникающих проблем. 

**Дополнение к списку инициатив:**

- Экспорт API в Spec Storage. Поддержание версионирования;
- Выделение отдельных БД для CRM и Shop API;
- Добавление в систему API Gateway
- Добавление в систему средств для повышения наблюдаемости: трассировка, логирование, сбор метрик, алерты.
