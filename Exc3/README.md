# Трассировка

## Компоненты для покрытия трейсингом. Потенциальные задержки.

**Формат** - <компонент>: [потенциальные проблемные места, вызывающие задержки]
- Shop API: запись в БД информации по заказам, загрузка схем в S3 Storage.
- CRM API: чтение из БД информации по заказам, чтение схем из S3 Storage, отправка сообщений о новых заказах в RabbitMQ
- MES API: обработка сообщений из RabbitMQ (расчет стоимости), загрузка моделей из S3 Storage, сохранение информации о расчетах и привязке оператора в БД, чтение из БД последних заказов.
- MES: получение списка заказов

## Мотивация

- Упрощает диагностику неисправностей в системе (Пример: пользователь на запрос создания заказа получает 500 Http code. Трассировка явно покажет, на каком шаге обработки запроса произошла проблема);
- Привносит ясность в ландшафт микросервисов. Трассировка может показать, что запрос к API вызывает цепочку вызовов к другим сервисам и базам данных;
- Позволяет точечно выявлять узкие места в системе (Пример: оператор жалуется на медленную загрузку страницы с заказами. Трассировка покажет неоптимальные запросы к БД или медленную загрузку моделей из S3 Storage).

Для осуществления трассировки в систему будет внедрен следующий стек: OpenTelemetry (для сбора и транспортировки трейсов), БД Cassanra (хранение трейсов), Jaeger в качестве UI для анализа и просмотра данных трассировки.

**Детали внедрения:**

- В каждый из сервисов необходимо добавить зависимость - библиотеку OpenTelemetry, которая будет собирать и отправлять трейсы на дальнейший процессинг;
- Развернут OpenTelemetry Collector - будет принимать трейсы от агентов\экспортеров и сохранять их в БД;
- Развернут кластер Cassandra с репликацией в формате master-slave;
- Установлен Jaeger в качестве UI для просмотра и анализа трейсов (будет смотреть в оптимизированную на чтение read-only реплику Cassandra).

## Компромиссы

Внедрение трейсинга будет затруднительным в системах, реализованных на устаревшем стеке технологий. В таком случае вряд ли найдутся готовые библиотеки и придется самостоятельно реализовывать экспортеры и агенты, что требует дополнительных ресурсов и удорожает создание и поддержку системы в целом.

В примере, описанном выше, можно пойти на компромисс и покрыть код "чекпойнтами", рассчитывая разницу времени между ними (+ сохранять показатели в БД). Это позволит оценить скорость выполнения отдельных участков кода, что может быть полезным при разборе проблем с производительностью.

## Безопасность

Все компоненты системы трассировки расположены внутри того же контура, что и элементы системы «Александрит», т.е закрыты для доступа из вне.
Анализ\просмотр трассировки осуществляется через Jaeger UI, доступ к которому закрыт SSO и управляется через LDAP группу tracing_view_users.
