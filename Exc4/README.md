# Архитектурное решение по логированию

## Какие логи нужно собирать
**Формат** - <уровень>: <описание>
- INFO: Информация о заказе успешно сохранена в БД
- ERROR: Запрос на создание заказа не прошел валидацию
- INFO: Изменение статуса заказа
- WARN: Заказ не был найден по его идентификатору
- INFO: Заказ назначен на оператора
- WARN: Список заказов не был загружен

## Мотивация

- Упрощает диагностику неисправностей в системе (позволяют понять, что происходило с системой ДО, ВО ВРЕМЯ и ПОСЛЕ сбоя);
- Мониторинг работы приложения (настройка дашбордов на основании кокретных логов и лейблов);
- Упрощает работу службы поддержки (логи помогают технической поддержке быстрее диагностировать и решать проблемы пользователей);
- Возможность проведения анализа использования системы (определить, какая функциональность системы используется чаще всего для предусмотрения дальнейших оптимизаций).

**Логгирование и трейсинг в первую очередь необходимы:**

- Shop API, поскольку именно он отвечает за предобработку и сохранение пользовательского заказа. В данном компоненте происходят чаще всего ошибки валидации (пользователь прикрепил некорректную модель, забыл добавить описание или указать контактные данные);
- Важно добавить логгирование в MES API, для упрощения разбора инцидентов, связанных с долгим изготовлением продукции (сможем посмотреть, на какого оператора был назначен заказ, когда произвенедн старт исполнения и заказа и другая информация, относящаяся к жизненному циклу изделия);
- Так же необходимо покрыть трассировкой сервисы, которые взаимодействуют с базами данных и очередью сообщений, т.к. именно данные интеграции могу быть подвержены сбоям и трудны в анализе.

Для осуществления логгирования в систему будет внедрен стандартный ELK стек.

**Детали внедрения:**

- В каждый из сервисов (контейнер) необходимо добавить агент - Filebeat, которая будет собирать и отправлять логи дальнейший процессинг в Logstash;
- Развернут Logstash в котором будут настроены правила для предварительной обработки и фильтрации логов: нормализация, фильтрация, сокрытие персональных данных и т.п;
- Развернут кластер OpenSearch с репликацией в формате master-slave;
- Установлена Kibana в качестве UI для просмотра и анализа логов (будет смотреть в оптимизированную на чтение read-only реплику OpenSearch).

В отношении логов будет представлена следующая **политика безопасности:**

- Все компоненты системы логгирования расположены внутри того же контура, что и элементы системы «Александрит», т.е закрыты для доступа из вне. Просмотр логов будет доступен узкому кругу лиц (тех. поддержка, разработчики, менеджер проекта) по SSO (личная LDAP учетка и наличие членства в группе kibana_readers);
- Персональные данные будут маскироваться на уровне приложение, а так же проходить через дополнительные проверки в Logstash. Таким образом в OpenSearch не будут храниться персональные данные пользователей системы.

**Дополнительные мероприятия:**

- Настроены дашборды для визуальной оценки состояния работы системы на основе логов (количество заказов в различных статусах)
- Настроен алертинг, на падение заказов в статусах CREATED и IN_PROGRESS (вероятно, что-то произошло с API. Новые заказы не создаются, а существующие не берутся в работу)
- Анализ числа ошибок валидации и авторизации. Резкий рост сигнализирует о попытках воздействия из вне. 

## Дополнения по результатам ревью

**Политика хранения логов:**

| Тип логов  | Уровни                   | Хранение в основном хранилище | Хранение в холодном хранилище | Ротация             | Безопасность                                                                    |
|------------|--------------------------|-------------------------------|-------------------------------|---------------------|---------------------------------------------------------------------------------|
| Системные  | INFO, WARN, ERROR        | 30 дней                       | 6 месяев                      | ежедневная          | шифрование при передаче и хранении, доступ только для системных администраторов |
| Приложения | DEBUG, INFO, WARN, ERROR | 10 дней                       | 6 месяев                      | по размеру > 256 МБ | на основе LDAP ролей                                                            |


**Метрики решения, на которые повлияет внедрение логирования:**

1. **Технические:**
    
    - Подсчет количества ошибок, возникающих в системе, на основе логов с уровнем ERROR. Фикс багов - повышение стабильности работы системы.
    - Выявление задержек межсервисного взаимодействия по логам уровня INFO. Принятие мер по оптимизации узких мест.
    - Доступность системы: по логам можно понять, функционируют ли компоненты системы штатно или есть проблемы.

2. **Бизнес:**

    - Логирование позволяет быстрее устранять ошибки системы, что напрямую влияет на удовлетворенность пользователей (Customer Satisfaction, CSAT);
    - Среднее время выполнения бизнес процесса: временна разница между записью "Order 123 created" и "Order 123 successfully completed"
    - Среднее время реагирования на инциденты (MTTR): логирование позволяет быстрее диагностировать проблемы и находить их корневые причины, что сокращает время на устранение инцидентов. Снижение MTTR с 1.5 часов до 30 минут.
