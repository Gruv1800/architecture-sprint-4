# Архитектурное решение по кешированию

## Мотивация

Кеширование будет добавлено в MES API для решения медленной загрузки перечня новых заказов, а так же заказов, назначенных на конкретного оператора. Как итог заказы будут быстрее приниматься в работу, что благоприятно скажется на скорости поставки готового результата конечному потребителю. 

## Предлагаемое решение

**Предлагаю внедрить серверное кеширование по ряду причин:**

- Обновление кэша не связаны с запросами операторов. Кеш будет обновляться\инвалидироваться по факту получения новых запросов на создание заказа и\или смене статуса заказа;
- В связи с предполагаемым ростом числа новых заказов, кеш, реализованный на клиентской стороне (или на стороне веб-сервера), будет быстро устаревать. Требование обработки новых заказов в первую очередь не будет выполняться;
- Возможность "прогрева" кеша данными из MES DB

**Применяемый паттерн кеширования - Write-Through:**

- Данные будут обновляться в кеше одновременно с записью в БД, т.о состояние кэша всегда будет актуальным. При сбоях или рестарте приложения, кеш будет программно наполняться данными из БД в момент старта.
- Снижается нагрузка на БД, т.к все запросы будут получать данные из кеша (cache miss сводится к минимуму);
- Cache-Aside не подходит из-за необходимости устанавливать низкий порог (TTL) инвалидации, что повлечет за собой большое количество запросов в БД. В противном случае операторы будут получать устарешние выборки.
- Refresh-Ahead не подходит из-за сложности реализации. В команде недостаточно ресурсов и есть более приоритетные бизнес задачи. 

**Стратегия инвалидации - программная при записи (Write-Through)**

В результате выбранной стратегии, данные в кеше будут всегда в актуальном состоянии, а также уходит необходимость в инвалидации по времени (своего рода экономия ресурсов). Следует читывать некоторые **особенности:** незначительно возрастает время записи, а так же разработчикам необходимо потратить чуть больше времени на реализацию данной стратегии (+ предусмотреть fallback в случае недоступности кеша) | Не подходит, т.к. изменение\создание заказов распределено не линейно во времени, что временами будет приводить к устареванию данных в кеше, а так же лишним инвалидациям (тогда, когда это не нужно).
